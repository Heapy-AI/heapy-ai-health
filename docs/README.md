# Heapy AI health care 파이프라인 — 설계 문서

Heapy AI health care의 요청 처리 파이프라인 설계 자료 모음이다. 멀티턴 대화, 검색 캐시, 스트리밍 응답을 포함한 RAG 기반 헬스케어 응답 시스템의 내부 구조를 정의하며, 팀 분업 개발의 기준 문서로 사용한다.

## 파이프라인 개요

사용자 질문은 세션 컨텍스트 로드 → 의도 분류 → (캐시 우선) 검색 → 프롬프트 구성 → 스트리밍 LLM 응답 → 히스토리 저장 순서로 처리된다. 의도(intent)에 따라 네 갈래로 분기한다.

| intent | 처리 | 개인 데이터 |
| --- | --- | --- |
| `simple_lookup` | VDB 검색으로 용어·정의 반환 | 불필요 |
| `comprehensive` | 다중 collection 검색 + 개인 데이터 결합 + 분석 | 필요 (검진/생활/복용금지) |
| `general_chat` | 검색 없이 자유 대화 | 불필요 |
| `ignore` | 주식·날씨·스포츠·코딩 등 건강 서비스 외 고정 문구 | 불필요 |

핵심 설계 결정은 다음과 같다. 파이프라인은 단일 State 객체를 노드에서 노드로 흘려보내며, 각 노드는 필요한 필드를 읽고 결과 필드를 채운다. VDB 검색 결과(청크)는 캐시하지만 개인 데이터(RDB)는 캐시하지 않는다. 로그인 사용자의 최근 메시지와 요약은 Supabase에서 로드하며, 답변 완료 시 한 트랜잭션으로 저장해 다음 턴이 사용한다.

현재 MVP는 `POST /chat`과 `POST /chat/stream`에서 Intent v7과 Safety Guard를 독립 실행한다. Guard는 Intent를 `ignore`로 덮어쓰지 않고 위험 수준과 금지 행동만 기록한다. `simple_lookup`과 `comprehensive`는 Pinecone 다중 namespace 병렬 검색을 사용하고, `general_chat`은 검색 없는 Gemini 대화, `ignore`는 건강 서비스 외 고정 응답을 사용한다. RAG 경로는 검색 결과 존재·최소 유사도·명시 대상 일치를 코드로 확인한 뒤 근거가 있는 질문 항목만 답한다. 완료 후 근거 충족도와 안전 정책 준수 여부를 감사하며 이미 표시된 본문은 교체하지 않는다. Supabase Auth, 사용자 프로필, 세션별 히스토리·요약 저장은 통합 엔드포인트에 연결되었다. 개인 검진 데이터 결합과 검색 캐시는 아직 연결되지 않았다.

시연용 웹 앱은 FastAPI의 `GET /`에서 제공하며 `POST /chat/stream`의 SSE 응답 계약을
사용한다. 사용자에게 보이는 답변 본문에서는 검증용 인용 라벨을 제거하고, 응답의
Intent, 신뢰도, 위험 수준, 검색 결과 검사, 사후 감사, 근거 청크, 전체 JSON을 우측 패널의 질문별
접이식 카드 목록에 표시한다.
포트 3000 사용자 UI는 프로젝트 검사 메뉴 대신 로그인 사용자의 Supabase 대화 세션
목록을 왼쪽에 표시하고, 선택한 세션의 저장 메시지와 요약을 복원한다.
세션을 불러오는 동안에는 답변 생성용 말풍선 로더를 재사용하지 않고 대화 영역 중앙에 전용 로딩 애니메이션을 표시한다.

웹 앱의 스트리밍 표시는 서버 수신과 분리된 프론트 표시 대기열을 사용한다. 서버는
토큰과 검증 완료 결과를 가능한 즉시 전달하고, 웹 앱은 글자·문장부호 단위의 짧은
간격으로 답변을 표시한다. `complete.answer`는 스트리밍 토큰을 연결한 본문과 동일하며,
표시 대기열이 끝난 후 사후 감사 카드만 추가한다.
최종 답변은 사용자가 먼저 인사한 경우가 아니라면 반복 인사나 자기소개 없이 질문의
핵심 내용부터 작성한다.
대화 시작 화면의 추천 질문은 별도 Gemini 호출 없이 검증된 건강정보 질문 풀에서
4개를 무작위 선택하며, 페이지 진입과 새 대화 시작 때 다시 구성한다.

웹 앱의 시각 테마는 Figma `Heapy_wireframes`의 `110:4515` 노드를 참고한다. 기존
데스크톱 3패널 정보 구조와 스트리밍 동작은 유지하고, 라벤더 배경·퍼플 포인트·
딥그린 타이포·화이트 라운드 카드 중심의 디자인 토큰만 반영한다.
브랜드 영역에는 `heapy-logo.png`, AI 상담사 영역에는 `heapy-doctor.png`를 사용한다.
좌측 패널은 별도 서비스 메뉴나 작은 카드 틀을 두지 않고 `GET /health` 응답을 사용해
벡터 백엔드, 임베딩 모델, Intent 분류기와 Pinecone 컬렉션별 적재 청크 수를 표시한다.
긴 모델명과 컬렉션명은 생략하지 않고 여러 줄로 표시한다.

## 문서 구성

읽는 순서대로

1. **[파이프라인 다이어그램](./index.html)** — 전체 흐름을 시각화한 인터랙티브 다이어그램. 브라우저에서 열면 확대/이동 가능. 여기서 전체 그림을 먼저 파악한다. (원본 Mermaid 코드는 `pipeline.mmd`)

2. **[노드 입출력 명세](./node-io-spec.md)** — 각 노드가 무슨 필드를 읽고 쓰는지 표로 정리. 분업 시 자기 노드의 입출력을 여기서 확인한다. 가장 자주 참조할 문서.

3. **[노드 함수 스텁](./node_stubs.py)** — 노드별 함수 시그니처(타입 힌트) + 실제 값 예시 + 분류 fixture. 타입 정의(Chunk, UserContext 등)와 코드로 표현된 계약. 실제 구현은 이 시그니처를 맞춘다.

4. **[State 설계 문서](./pipeline-state-design.md)** — 왜 이런 구조인지, State 라이프사이클, 직렬화 경계 등 설계 배경. 구현 중 "왜 이렇게 했지" 싶을 때 참조.

5. **[응답 설계 문서](.response_schema.py)** - intent 4개 분기별 최종 응답 JSON 구조와 예시. 어떤 분기에 어떤 필드(personal_data, next_action 등)가 들어가는지 정의. 파이프라인이 클라이언트에 내보내는 계약이므로, 백엔드뿐 아니라 프론트 개발자도 참조한다.

6. **[다중 컬렉션 병렬 검색 방법론](./multi_collection_parallel_retrieval.md)** — Sub-intent 분류기 없이 여러 Pinecone namespace를 병렬 검색하고 결과를 병합하는 기준. 검색 상수는 전체 데이터 적재 후 평가를 통해 확정한다.

7. **[Supabase 인증·대화 DB 설계](./supabase_auth_chat_db_design.md)** — Auth 계정과 공개 프로필의 연결, 기존 사용자 보존, RLS, 세션·메시지·요약 저장 경계.

## 분업 가이드

담당 노드를 정한 뒤 다음 순서로 진행한다. 먼저 다이어그램에서 자기 노드의 위치와 앞뒤 연결을 확인하고, 노드 입출력 명세에서 읽을 필드와 쓸 필드를 파악한 다음, 함수 스텁에서 타입 시그니처와 예시 값을 보고 구현한다.

노드는 크게 다음 영역으로 나뉜다. 세션·컨텍스트 관리(S1-S4), 의도 분류(A1-A4), 검색(캐시 조회/VDB/캐시 저장), 개인 컨텍스트 수집(AUTH/D1/D2, comprehensive 전용), 프롬프트 구성 및 LLM(C2/B4/C5, L1-L3, B5)이다.

## 팀 합의 필요 사항

분업 시 노드 간 인터페이스가 어긋나기 쉬운 지점이다. 구현 전에 합의한다.

1. **`query_embedding` 재사용** — A1에서 한 번 생성한 벡터를 캐시 조회·검색·캐시 저장이 공유한다. 각 노드에서 다시 임베딩하지 않는다.

2. **`chunks`의 세 가지 상태** — `None`은 검색 인프라 실패(에러 분기), `[]`는 결과 0건(일반 대화 전환), 값이 있으면 정상이다. 검색 담당자는 이 규약대로 반환해야 뒤 분기가 동작한다.

3. **개인 데이터 캐시 금지** — 검진·생활·복용금지 등 RDB 개인 데이터는 사용자·시점마다 달라지므로 캐시하지 않는다. VDB 청크만 캐시한다.

4. **요약 생성/로드 분리** — 요약은 응답 후 히스토리 저장(O3)에서 갱신하고, 다음 턴의 컨텍스트 로드(S2)는 이를 읽기만 한다. S2에서 요약을 새로 만들지 않는다.

5. **판정 기준 고정 전제** — Labs Item Master의 판정 기준은 이 파이프라인 범위에서 고정으로 본다. Labs Records의 status는 저장 시점에 이미 판정된 값이며, 조회 파이프라인은 읽기만 한다(재계산 없음). 기준 변경 시 과거 데이터 재판정은 별도 마이그레이션 배치가 담당한다.

## 미정 / 추후 확정

- **복용금지 목록 RDB 스키마** — Q3("함께 복용 가능?")가 comprehensive로 분류되며 사용자별 복용금지 목록 대조가 필요하다. 해당 RDB 스키마는 미정이며, 확정 후 `UserContext`에 필드를 추가하고 D2 조회 로직을 연결한다.
- **복약·생활 기록 데이터** — 데이터 스키마 문서에 추가 예정으로 표시된 항목. Q5(생활 데이터 활용)와 연결된다.
- **추이 delta 계산 위치** — 검진 추이 질문에서 변화량 계산을 D2(사전 계산)에서 할지 B4(LLM에 원본 전달)에서 할지 미정. 의료 수치 정확도를 고려해 결정한다.
