## 1. 기능 개발 파트의 발표 목표

이 파트가 끝났을 때 청중은 다음 흐름을 이해할 수 있어야 한다.

> HEAPY는 질문을 바로 LLM에 전달하지 않는다. 먼저 위험한 요청을 확인하고 질문의 의도를 분류한 뒤, 건강정보 검색이 필요한 질문만 여러 지식베이스에서 근거를 찾는다. 이후 LLM이 검색 근거를 바탕으로 답변 계획을 세우고, 최종 답변을 생성한 다음 근거에서 벗어난 내용이 없는지 다시 확인한다.

발표의 중심 흐름은 아래와 같다.

```text
사용자 질문
→ Safety Guard
→ Intent 분류
→ Intent별 처리 경로 선택
→ 필요한 경우 RAG 검색
→ LLM 계획·생성·검증
→ 최종 답변
```

기술을 하나씩 나열하기보다, **사용자 질문 한 건이 어떤 과정을 거쳐 답변이 되는지**를 순서대로 설명한다.

## 2. 권장 슬라이드 구성

기능 개발 파트는 총 5장으로 구성한다.

1. 챗봇 전체 파이프라인과 Safety Guard
2. Intent 분류기와 4개 Intent
3. Intent 학습 과정과 검증 결과
4. RAG 다중 병렬 검색과 결과 병합
5. LLM 계획·생성·검증 역할 분리

스트리밍 구현은 이번 기능 개발 파트에서 제외한다. 데모 서비스 구현 현황에서 화면 동작을 보여줄 때만 자연스럽게 확인되도록 한다.

## 3. 슬라이드별 내용

### 4-1. 질문에 따라 필요한 처리 경로를 선택한다

#### 이 슬라이드의 역할

처음 보는 청중에게 HEAPY 챗봇의 전체 구조를 먼저 보여준다. 이후 설명할 Intent, RAG, LLM이 전체 과정의 어느 위치에 있는지 이해시키는 슬라이드다.

#### 슬라이드 제목

> 질문을 바로 답변하지 않고, 안전 확인과 의도 분류부터 시작합니다

#### 슬라이드에 보일 내용

```text
사용자 질문
     ↓
Safety Guard
     ↓
Intent v6 분류기
     ↓
┌──────────────┬──────────────┬──────────────┐
공공정보 RAG   강화 RAG       일반 대화      고정 응답
simple_lookup  comprehensive  general_chat   ignore
     ↓              ↓              ↓              ↓
        의도에 맞는 최종 답변 생성
```

#### Safety Guard 설명

Safety Guard는 **Intent 분류기보다 먼저 실행되는 규칙 기반 안전 필터**다.

다음과 같이 챗봇이 대신 결정해서는 안 되는 요청을 탐지한다.

- 질환 여부를 확정해 달라는 요청
- 약의 용량·중단·변경을 결정해 달라는 요청
- 병원이나 응급실에 가야 하는지 판단해 달라는 요청

탐지된 질문은 Intent 분류와 검색을 진행하지 않고 `ignore` 경로로 보낸다.

#### 발표자가 설명할 내용

> HEAPY는 모든 질문을 같은 방식으로 처리하지 않습니다. 먼저 규칙 기반 Safety Guard가 진단이나 처방처럼 챗봇이 직접 결정하면 위험한 요청을 확인합니다. 안전 검사를 통과한 질문은 Intent 분류기가 질문의 목적을 네 가지로 나누고, 각 목적에 맞는 검색 또는 응답 경로를 선택합니다.

#### 추천 시각 자료

이 슬라이드에서는 복잡한 시스템 아키텍처보다 **질문이 위에서 아래로 이동하는 단일 흐름도**를 사용한다. 네 가지 Intent 경로만 가운데에서 갈라지게 표현한다.

### 4-2. Intent v6가 질문을 네 가지 목적에 따라 분류한다

#### 이 슬라이드의 역할

왜 질문을 분류하는지와 각 Intent가 실제로 어떤 처리 경로를 선택하는지 설명한다.

#### 슬라이드 제목

> 네 가지 Intent가 검색과 LLM 사용 여부를 결정합니다

#### 슬라이드에 보일 내용

| Intent | 질문의 목적 | 실제 처리 |
|---|---|---|
| `simple_lookup` | 일반 건강·질환·검사·의약품 정보를 묻는 질문 | 공공 VDB 기반 RAG |
| `comprehensive` | 사용자의 건강·검진·복약 데이터를 함께 봐야 하는 질문 | 강화 RAG, 개인 데이터 연동 예정 |
| `general_chat` | 일상 대화, 감정 표현, 가벼운 건강 대화 | 검색 없이 Gemini 응답 |
| `ignore` | 서비스 범위 밖 질문 또는 의료적 결정을 요구하는 질문 | LLM·검색 없이 고정 응답 |

#### 질문 예시

| Intent | 예시 질문 |
|---|---|
| `simple_lookup` | “공복혈당이 높으면 어떤 의미야?” |
| `comprehensive` | “내 검진 결과와 복용 중인 약을 같이 보고 설명해줘.” |
| `general_chat` | “요즘 건강 관리가 너무 귀찮아.” |
| `ignore` | “혈압약을 두 알로 늘려도 돼?” |

#### 발표자가 설명할 내용

> Intent 분류기의 목적은 질문에 이름을 붙이는 것이 아니라 처리 경로를 선택하는 것입니다. 일반 건강정보 질문은 RAG로 보내고, 개인 데이터가 필요한 질문은 더 엄격한 검증 경로로 보냅니다. 일상 대화는 검색을 생략하고, 서비스 범위 밖이거나 의료적 결정을 요구하는 질문은 고정 응답으로 종료합니다.

#### 현재 구현 범위

- `simple_lookup`, `general_chat`, `ignore` 경로는 현재 동작한다.
- `comprehensive`의 분류와 강화 검증 경로는 동작한다.
- 개인 건강검진 RDB는 연결되어 `comprehensive`가 질문 관련 검진 결과와
  공용 의학 근거를 결합한다. 복약·생활 기록 RDB는 아직 연결되지 않았다.

### 4-3. 라벨링한 질문 데이터로 경량 Intent 분류기를 학습했다

#### 이 슬라이드의 역할

Intent 분류기를 어떤 데이터와 방식으로 만들었는지, 실제 성능이 어느 정도인지 보여준다.

#### 슬라이드 제목

> 직접 라벨링한 질문으로 4개 Intent 분류기를 학습하고 검증했습니다

#### 학습 과정

```text
1. Intent별 질문 기준 정의
        ↓
2. 질문 문장에 4개 Intent 라벨 부여
        ↓
3. 학습·검증·테스트 데이터 분리
        ↓
4. Ko-SRoBERTa로 질문을 768차원 벡터로 변환
        ↓
5. Linear Layer와 Softmax 학습
        ↓
6. Test와 Blind 질문으로 최종 검증
```

#### 데이터 구성

| 구분 | 문장 수 | 사용 목적 |
|---|---:|---|
| Train | 631 | Linear Layer 학습 |
| Validation | 79 | 최적 모델 선택 |
| Test | 79 | 최종 성능 평가 |
| Blind | 48 | 학습·선택에 사용하지 않은 추가 검증 |

#### 모델 구성

```text
질문
→ jhgan/ko-sroberta-multitask 임베딩 768차원
→ Linear Layer
→ Softmax
→ simple_lookup / comprehensive / general_chat / ignore
```

- 문장 임베딩 모델은 동결하고 Linear Layer만 학습했다.
- 가장 높은 Validation Macro F1을 기록한 모델을 선택했다.
- 신뢰도 0.55 미만의 결과는 `uncertain`으로 표시한다.

#### 검증 결과

| 평가 데이터 | 방식 | Accuracy | Macro F1 |
|---|---|---:|---:|
| Validation | Linear classifier | 0.9747 | 0.9747 |
| Test | Linear + Safety Guard | 0.9367 | 0.9379 |
| Blind 48 | Linear + Safety Guard | 0.9583 | 0.9580 |

#### 발표에서 강조할 수치

> Test 기준 정확도 93.67%, Macro F1 93.79%

Validation 성능 97%보다 Safety Guard까지 포함된 Test 결과를 대표 수치로 사용한다.

#### 발표자가 설명할 내용

> 저희가 정의한 네 가지 Intent 기준에 맞춰 질문 문장을 직접 라벨링했습니다. 한국어 문장 임베딩 모델은 고정하고, 질문 벡터를 네 가지 Intent로 나누는 선형 분류기만 학습했습니다. 최종 Test에서는 정확도 93.67%, Macro F1 93.79%를 기록했습니다. 현재는 일반적인 증상 설명과 개인 증상 서술의 경계, 일부 안전 요청의 ignore 판별이 상대적으로 어려운 사례입니다.

### 4-4. RAG는 관련 컬렉션을 모두 검색한 뒤 근거를 병합한다

#### 이 슬라이드의 역할

Intent 분류 이후 `simple_lookup`과 `comprehensive` 질문이 어떻게 지식베이스를 검색하는지 설명한다. Collection Router를 추가하지 않은 설계 이유도 함께 보여준다.

#### 슬라이드 제목

> 소수의 지식 영역을 모두 병렬 검색해 근거 누락을 줄였습니다

#### 현재 검색 대상

| Pinecone namespace | 포함 정보 |
|---|---|
| `health_checkup_info` | 건강검진 항목과 수치 해석 정보 |
| `disease_info` | 질환 정의와 증상 정보 |
| `medication_info` | 의약품 효능·용법·주의사항 |

의약품 상호작용 데이터를 추가하면 검색 영역은 최대 4개 수준이다. 현재 실제 검색 설정에는 위 세 namespace가 연결돼 있다.

#### 검색과 병합 과정

```text
simple_lookup 또는 comprehensive 질문
        ↓
질문 임베딩 1회 생성
        ↓
┌────────────────┬────────────────┬────────────────┐
건강검진 검색     질환 검색         복약 검색
└────────────────┴────────────────┴────────────────┘
        ↓ 병렬 실행
검색 후보 통합
        ↓
중복 제거 → 최소 점수 적용 → 점수순 정렬 → 컬렉션 편중 제한
        ↓
최종 근거 청크 선택
```

#### 처음 검토한 방식: Collection Router

처음에는 질문을 한 번 더 분류해 검색할 컬렉션을 선택하는 Sub-intent 분류기를 고려했다.

```text
질문 → Collection Router → 선택된 컬렉션만 검색
```

하지만 이 방식에는 다음 위험이 있다.

- 한 질문이 질환·검진·복약 정보를 동시에 필요로 할 수 있다.
- 다중 라벨 분류가 틀리면 관련 컬렉션 자체가 검색에서 제외된다.
- 새로운 컬렉션을 추가할 때 라우터 데이터와 모델도 다시 관리해야 한다.
- 현재 검색 영역이 3개이고 추가 예정 영역을 포함해도 4개 수준이라 전체 검색 비용이 감당 가능하다.

#### 최종 선택: 전체 병렬 검색

> 컬렉션 선택 정확도를 별도로 관리하기보다, 소수의 컬렉션을 모두 검색하고 검색 결과의 점수와 병합 규칙으로 최종 근거를 선택했다.

#### 현재 병합 기본값

- 컬렉션별 검색 후보: 3개
- 최종 근거 청크: 최대 6개
- 한 컬렉션의 최종 포함 수: 최대 2개
- 중복 결과 제거 후 유사도 점수순 정렬

#### 발표자가 설명할 내용

> 처음에는 질문에 따라 검색할 컬렉션을 고르는 Collection Router를 추가하려고 했습니다. 하지만 건강 질문은 질환, 검진, 복약 정보가 겹치는 경우가 많고, Router가 컬렉션 하나를 누락하면 그 안의 근거는 처음부터 찾을 수 없습니다. 현재 검색 영역은 세 개이고 향후 추가 영역을 포함해도 네 개 수준이므로, 모든 영역을 동시에 검색한 뒤 결과를 합치는 방식을 선택했습니다. 검색 결과에서는 중복을 제거하고 점수순으로 정렬하며, 한 컬렉션에 결과가 과도하게 몰리지 않도록 제한합니다.

#### 발표 시 주의사항

- “모든 컬렉션을 검색하므로 정확하다”가 아니라 “Router 단계에서 발생할 수 있는 컬렉션 누락을 줄였다”고 표현한다.
- 검색 정확도는 데이터 적재 완료 후 별도의 Retrieval 평가로 검증해야 한다.
- 현재 최소 유사도와 Top-K는 구조 검증용 기본값이다.

### 4-5. LLM의 역할을 계획·생성·검증으로 분리했다

#### 이 슬라이드의 역할

검색된 청크가 바로 답변이 되는 것이 아니라, LLM이 근거를 정리하고 답변을 만든 뒤 다시 확인하는 과정을 설명한다.

#### 슬라이드 제목

> 하나의 프롬프트에 모든 역할을 맡기지 않고 세 단계로 분리했습니다

#### 역할 분리

| 단계 | LLM의 역할 | 출력 |
|---|---|---|
| 계획 | 검색 청크만으로 질문에 답할 수 있는지 판단하고 사용할 사실을 정리 | `answerable`, 사실 목록, 근거 청크 ID |
| 생성 | 승인된 사실만 사용해 사용자에게 보일 답변 작성 | 최종 한국어 답변 |
| 검증 | 최종 답변이 승인된 사실과 검색 근거를 벗어났는지 확인 | 통과 여부, 미지원 주장 |

#### 전체 흐름

```text
RAG 검색 청크
→ 근거 계획 생성
→ 계획 검증
→ 최종 답변 생성
→ 사후 검증
```

검색 근거가 부족하거나 계획이 승인되지 않으면 최종 답변을 생성하지 않고 다음 고정 결과를 반환한다.

> 지식베이스에 근거 없음

#### 근거 계획 프롬프트 예시

실제 `GROUNDING_PLAN_PROMPT`에서 발표에 필요한 부분만 보여준다.

```text
너는 HEAPY 건강정보 답변의 근거 설계자다.
사용자에게 답변을 보여주기 전에 검색 청크만으로
답할 수 있는지 판단하고 근거 계획을 작성하라.

규칙
1. 검색 청크가 직접 뒷받침하는 사실만 facts에 넣는다.
2. 각 사실에는 실제 근거 청크 ID를 연결한다.
3. 근거가 부족하면 answerable=false로 설정한다.
4. 존재하지 않는 청크 ID를 만들지 않는다.
```

#### 최종 답변 프롬프트 예시

```text
승인된 근거 계획만 사용해 최종 한국어 답변을 작성하라.
근거 계획에 없는 건강·의료 사실, 수치, 원인, 관계를 추가하지 않는다.
청크 ID나 인용 라벨은 사용자 답변 본문에 표시하지 않는다.
```

#### 사후 검증 프롬프트 예시

```text
최종 답변의 모든 건강·의료 사실이
승인된 근거 계획과 검색 청크의 뒷받침을 받는지 확인하라.
계획에 없는 주장이 추가되면 unsupported로 기록한다.
```

#### 발표자가 설명할 내용

> RAG가 찾은 문서를 그대로 LLM에 넣고 바로 답변하게 하지 않았습니다. 첫 번째 LLM은 검색 청크에서 실제로 사용할 수 있는 사실과 그 근거를 정리합니다. 두 번째 LLM은 승인된 사실만 사용해 최종 답변을 만듭니다. 세 번째 LLM은 답변이 승인된 사실을 벗어나지 않았는지 다시 확인합니다. 세 역할을 분리해 어떤 근거가 답변에 사용됐는지 추적할 수 있도록 했습니다.

#### 발표에서 과장하지 않을 부분

- 계획과 검증도 LLM을 사용하므로 답변 정확성을 완전히 보장하는 장치는 아니다.
- 현재 구조는 근거 사용 과정을 제한하고 추적하기 위한 장치다.
- 검증기의 실제 성능은 별도의 근거 일치 평가셋으로 측정해야 한다.

---

## 4. 근거 계획이란 무엇인가

### 한 문장 설명

> 근거 계획은 최종 답변을 쓰기 전에 “이 질문에 답할 수 있는가, 어떤 사실을 사용할 것인가, 각 사실은 어느 검색 청크가 뒷받침하는가”를 구조화한 내부 체크리스트다.

근거 계획은 사용자가 보는 답변 초안이 아니다. LLM의 자유로운 추론 과정을 저장하는 것도 아니다. **최종 답변에서 사용해도 되는 사실의 허용 목록**에 가깝다.

### 실제 구조 예시

질문이 다음과 같다고 가정한다.

> 공복혈당이 높으면 어떤 의미야?

검색 결과에서 관련 청크가 확인되면 내부적으로 다음과 같은 계획을 만든다.

```json
{
  "answerable": true,
  "facts": [
    {
      "statement": "공복혈당은 일정 시간 금식 후 측정한 혈당 수치다.",
      "cited_chunk_ids": ["C1"]
    },
    {
      "statement": "공복혈당 상승은 혈당 조절 상태를 확인할 때 참고할 수 있다.",
      "cited_chunk_ids": ["C1", "C2"]
    }
  ],
  "reason": "질문의 정의와 해석에 필요한 근거가 검색 청크에 포함돼 있다."
}
```

최종 답변 생성기는 위 `facts`에 들어 있는 내용만 사용한다. 검색 청크에 없는 구체적인 원인이나 진단을 임의로 추가하지 못하도록 제한한다.

### 왜 필요한가

일반적인 RAG는 검색 문서를 LLM에 전달하고 바로 답변을 생성하는 경우가 많다.

```text
검색 문서 → 최종 답변
```

HEAPY는 그 사이에 근거 계획을 추가했다.

```text
검색 문서 → 사용할 사실과 근거 확정 → 최종 답변
```

이 단계가 있으면 다음 내용을 확인할 수 있다.

- 검색된 문서만으로 질문에 답할 수 있는지
- 최종 답변에서 사용할 사실이 무엇인지
- 각 사실이 어떤 검색 청크와 연결되는지
- 근거가 부족할 때 답변 생성을 중단해야 하는지

### 근거 계획 승인이라는 표현의 의미

현재 구현에서 “승인”은 사람이 직접 확인하고 버튼을 누른다는 뜻이 아니다.

다음 조건을 코드가 확인한다.

1. 계획의 `answerable`이 `true`인지
2. 사용할 `facts`가 비어 있지 않은지
3. 각 사실에 근거 청크 ID가 연결돼 있는지
4. 계획에 적힌 청크 ID가 실제 검색 결과에 존재하는지

이 조건을 통과하면 최종 답변 생성 단계로 이동한다. 통과하지 못하면 `지식베이스에 근거 없음`을 반환한다.

### 한계

구조 검증을 통과했다고 해서 해당 사실의 의미가 100% 정확하다는 뜻은 아니다. 현재는 `comprehensive` 또는 Intent 신뢰도가 낮은 질문에서 의미 일치 여부를 더 엄격하게 확인하지만, 계획 자체도 LLM이 생성한다.

따라서 발표에서는 다음처럼 표현하는 것이 적절하다.

> 검색 근거에서 사용할 사실과 청크 연결을 먼저 구조화하고, 기본 조건을 통과한 계획만 최종 답변에 사용한다.

“LLM 답변의 사실성을 완전히 검증했다”는 표현은 사용하지 않는다.

## 5. 기능 개발 파트 전체 발표문 초안

> HEAPY 챗봇은 사용자의 질문을 바로 LLM에 전달하지 않습니다. 먼저 규칙 기반 Safety Guard가 진단, 약물 변경, 내원 여부처럼 챗봇이 대신 결정하면 위험한 요청을 확인합니다. 이후 Intent v6가 질문을 일반 건강정보 조회, 개인 데이터 기반 종합 질문, 일반 대화, 서비스 범위 밖 요청의 네 가지로 분류합니다.
>
> Intent 분류기는 저희가 직접 라벨링한 질문 데이터를 사용해 학습했습니다. 한국어 문장 임베딩 모델로 질문을 768차원 벡터로 변환하고, 선형 분류기가 네 가지 Intent를 선택합니다. 최종 Test에서 정확도 93.67%, Macro F1 93.79%를 기록했습니다.
>
> 일반 건강정보 조회와 종합 질문은 RAG 경로로 이동합니다. 처음에는 질문에 따라 검색할 컬렉션을 고르는 Collection Router를 고려했지만, 건강 질문은 질환, 검진, 복약 정보가 함께 필요한 경우가 있고 Router가 한 영역을 누락하면 그 안의 근거를 찾을 수 없습니다. 현재 검색 영역이 세 개이고 추가 예정 영역을 포함해도 네 개 수준이므로, 모든 영역을 병렬 검색한 뒤 결과를 병합하는 방식을 선택했습니다.
>
> 병합된 검색 결과는 바로 답변으로 생성하지 않습니다. 먼저 검색 청크만으로 답할 수 있는지 확인하고, 사용할 사실과 근거 청크를 근거 계획으로 정리합니다. 계획을 통과한 사실만 사용해 최종 답변을 생성하고, 생성된 답변이 승인된 사실을 벗어나지 않았는지 다시 검증합니다. 이를 통해 질문 분류부터 검색 근거, 최종 답변까지의 처리 과정을 추적할 수 있도록 구성했습니다.

## 6. 발표 자료 작성 시 제외하거나 축소할 내용

이번 기능 개발 파트에서는 다음 내용을 별도 슬라이드로 만들지 않는다.

- LLM 응답 스트리밍 방식
- 프론트엔드의 글자 표시 속도
- 우측 모니터링 카드의 상세 UI
- 전체 응답 JSON 구조
- Pinecone namespace별 정확한 적재 건수
- 향후 개발 계획과 전체 이슈 목록

위 내용은 각각 데모 서비스 구현 현황, 데이터 구성 현황, 이후 개발 계획 파트에서 필요한 경우 설명한다.

## 7. 발표 전 확인할 사항

1. `comprehensive`는 건강검진 RDB만 연동되었으며 복약·생활 데이터는
   미연동임을 분명히 표현하기
2. Intent 대표 수치는 Test Accuracy 93.67%, Macro F1 93.79%로 통일하기
3. 현재 활성 검색 영역은 3개, 추가 예정 영역 포함 최대 4개라는 표현 통일하기
4. Collection Router를 사용하지 않은 이유를 비용보다 **근거 누락 방지** 중심으로 설명하기
5. 근거 계획을 사람의 수동 승인처럼 설명하지 않기
6. 사후 검증이 정확성을 완전히 보장한다고 표현하지 않기
7. LLM 프롬프트는 전체 원문이 아니라 역할을 보여주는 핵심 규칙만 제시하기
