# 오늘의 건강 종합 점수 — 백엔드에서 해야 할 일

오늘의 건강 종합 점수 계산이 FastAPI로 넘어왔다(`heapy-health-v1`). Spring은 **호출·저장·조회**를
맡는다. 이 문서는 백엔드 쪽에 필요한 변경만 정리한다.

계산 규칙은 [오늘의 건강 종합 점수 기준](오늘의_건강_종합점수_기준.md)을 볼 것.

---

## 1. 왜 옮겼나

점수의 수면 성분이 네 가지로 늘었고, 그중 셋(규칙성·안정성·사회적 시차)은 **취침·기상
시각의 원형 통계**로 잰다. 시각은 자정에서 되감기는 값이라 보통의 평균·표준편차를 쓰면
틀린다. 이 계산은 생활건강 탭이 쓰려고 이미 Python에 검증된 채로 있었다.

Java로 다시 구현하면 두 벌이 되어 반드시 갈라진다. 판정 문턱(30·60·45분)도 생활건강
탭과 같은 값을 써야 하는데, 그 값들은 판정기준 문서와 테스트로 Python 쪽에 묶여 있다.

## 2. 호출 — `category`와 `scoreDays`

기존 `POST /internal/health/analyses`에 **`category: "score"`가 추가**되었다.

```json
{
  "contractVersion": "1.0",
  "category": "score",
  "analysisDate": "2026-09-10",
  "cutoff": "2026-09-09T15:00:00Z",
  "age": 35,
  "sex": "male",
  "scoreDays": 30,
  "records": { "sleep": [...], "activity": [...], "exercise": [...], "bio": [...] }
}
```

### `scoreDays` — 며칠치를 한 번에 낼지

`score`에서만 쓴다. **분석일까지 며칠치 점수를 한 번에 낼지**를 정한다. 기본값은 1이라
필드를 안 보내면 예전과 똑같이 하루치만 나온다.

그래프를 채우려면 하루에 한 번씩 30번 부를 이유가 없다. 스냅샷은 어차피 같은 것이
넘어오고, 서버 쪽 계산은 기준일만 하루씩 옮기는 일이다. **한 번 불러 `points`를 받아
그대로 `lifestyle_daily_scores`에 넣으면 된다.**

상한은 90이다. 하루치 점수가 최대 90일 전 기록까지 거슬러 보기 때문이다(BMI 90일,
활동 14일, 수면 8일). 창을 180일로 두었으므로 90일치 계열까지는 첫날도 과거를 온전히
보고 계산된다. 그보다 길게 달라고 하면 422로 거절한다.

**주의.** `records`에는 계열의 첫날이 거슬러 볼 만큼의 과거가 들어 있어야 한다.
`scoreDays: 30`이면 최소 120일치 기록을 보내야 첫날도 제대로 나온다. 모자라면 그날들은
`total_score: null`에 `reasons`가 붙어 돌아온다. 틀린 점수가 나오지는 않는다.

`HealthAnalysisSnapshot`이 이미 `HealthMetric` 전체를 넘기고 있어 수면의 `start_at`·`end_at`,
활동의 `steps`, 운동의 `duration_seconds`, 체성분의 `bmi_value`가 모두 들어온다.
**스냅샷 생성 코드는 그대로 두고 `category`만 `"score"`로 주면 된다.**

`checkups`도 그대로 쓴다. **생활 기록에 BMI·혈압·공복혈당이 없으면 검진에서 가져온다.**
체중계를 쓰지 않는 사용자는 지금 `bmi_missing`으로 총점이 아예 나오지 않는데, 검진에는
이 셋이 반드시 있다. 생활 기록은 90일, 검진은 365일까지 유효하다. 어디서 왔는지는
각 성분의 `source`에 `lifestyle` 또는 `checkup`으로 남는다.

혈압과 공복혈당은 **한 번 잰 값으로 판정하지 않는다.** 하루에 여러 번 잰 값을 그날
평균으로 묶고, 최근 측정일에서 거슬러 30일 안의 일별 값을 다시 평균한다. 평균에 든 날
수가 `recorded_days`에 남으므로 1이면 한 번 잰 값이라는 뜻이다.

`age`가 없으면 점수를 내지 않는다(`age_unavailable`). 만 20세 미만도 내지 않는다.

## 3. 응답 — `report`가 아니라 `score`다

점수는 모델을 부르지 않는 순수 계산이라 `headline`이 없다. 그래서 `report` 대신 `score`
키로 돌려준다.

### 게이트웨이 — 반영 완료

`HealthAnalysisGateway.java`가 이렇게 검증하고 있었다.

```java
if ("generated".equals(status) && (!result.path("report").isObject()
        || !result.path("report").path("headline").isTextual())) throw new IllegalArgumentException();
```

점수에는 `report`도 `headline`도 없으므로 이 검증을 타면 무조건 실패한다. 그래서
**`score(...)` 전용 메서드를 따로 두었다.**

```java
gateway.generate(snapshot)   // 분석 문장. report.headline 을 본다.
gateway.score(snapshot)      // 점수. score 객체와 points 배열을 본다.
```

HTTP 호출은 `post(snapshot, scoring)` 하나로 합쳤다. 오류 문구를 감싸는 자리도 하나라
건강 입력이나 공급자 오류가 새어 나가지 않는 성질은 그대로다.

### 응답 상한을 나눴다 — 64KiB로는 모자란다

점수 하루치는 성분과 근거까지 담아 **약 1.3KB**다. 실측값이다.

| 기간 | 응답 크기 |
|---|---|
| 7일 | 약 10KB |
| 30일 | 약 39KB |
| 90일 | 약 117KB |

분석 문장과 같은 64KiB를 쓰면 **50일쯤에서 잘린다.** 그래서 상한을 갈랐다.

```java
REPORT_LIMIT = 65536      // 분석 문장. 기존 그대로.
SCORE_LIMIT  = 1048576    // 점수. 90일치에 여유를 둔 값.
```

요청 상한 262,144바이트는 손대지 않았다. 스냅샷은 분석 문장과 같은 것을 쓰므로 점수라고
더 커지지 않는다. 다만 기록이 아주 많은 사용자는 이 상한에 먼저 걸린다. 점수 때문에
생긴 문제가 아니라 원래 있던 제약이다.

### 기록이 모자랄 때

```json
{
  "status": "data_insufficient",
  "score": {
    "policy_version": "heapy-health-v1",
    "score_date": "2026-09-10",
    "total_score": null,
    "components": {},
    "weights": {},
    "coverage": 0.0,
    "reasons": ["sleep_insufficient", "activity_insufficient", "bmi_missing"]
  }
}
```

`status`는 지금처럼 `generated` / `data_insufficient` 둘뿐이다. `total_score`가 `null`이면
`data_insufficient`이고 그 반대도 성립한다.

### `points` — 날짜순 계열

응답에는 `score`와 함께 **`points`가 언제나 들어 있다.** 위에 보인 `score`와 똑같은
모양의 객체가 날짜 오름차순으로 담긴다.

```json
{
  "status": "generated",
  "score":  { "score_date": "2026-09-10", "total_score": 77, ... },
  "points": [
    { "score_date": "2026-09-06", "total_score": 71, ... },
    { "score_date": "2026-09-07", "total_score": 74, ... },
    { "score_date": "2026-09-08", "total_score": 69, ... },
    { "score_date": "2026-09-09", "total_score": 75, ... },
    { "score_date": "2026-09-10", "total_score": 77, ... }
  ]
}
```

두 가지를 보장한다.

- `points`의 마지막 원소는 `score`와 **같은 객체다.** 마지막 날이 곧 분석일이다.
- `points`의 길이는 `scoreDays`와 같다. 기본값이면 1이다.

`status`는 마지막 날 하나만 보고 정한다. 계열 중간에 기록이 모자란 날이 섞여 있어도
분석일 점수가 나왔다면 `generated`다. **날짜별 성패는 각 원소의 `total_score`로 판단해야
한다.** `status` 하나로 30일치를 버리면 안 된다.

## 4. 저장 — 기존 테이블에 그대로 들어간다

`lifestyle_daily_scores`의 열에 이렇게 대응한다.

| 테이블 열 | 응답 경로 |
|---|---|
| `policy_version` | `score.policy_version` |
| `score_date` | `score.score_date` |
| `total_score` | `score.total_score` |
| `sleep_score` | `score.components.sleep.score` |
| `sleep_recorded_days` | `score.components.sleep.recorded_days` |
| `activity_score` | `score.components.activity.score` |
| `activity_recorded_days` | `score.components.activity.recorded_days` |
| `bmi_score` | `score.components.bmi.score` |
| `bmi_date` | `score.components.bmi.measured_date` |
| `reasons` | `score.reasons` |

기존 CHECK 제약과 어긋나지 않는다. **필수 성분**인 수면·활동·BMI가 모두 서고 `reasons`가
비었을 때만 `total_score`가 나오며, 그때 `sleep_recorded_days >= 5`,
`activity_recorded_days >= 7`, `bmi_date`가 모두 보장된다.

**대사는 선택 성분이라 비어 있어도 총점이 나온다.** 혈압계·혈당계가 없으면 쌓이지 않는
값이라 필수로 두면 대부분의 사용자가 점수를 받지 못한다. 이때 `score_coverage`가 0.9가
되므로, 기존 제약에 대사 관련 조건을 추가하면 안 된다.

### 마이그레이션이 필요하다

두 가지 때문이다.

**하나. 수면 기록 일수 상한.** 충분성의 창이 8일이라 기존 CHECK가 걸린다.

```sql
sleep_recorded_days smallint not null check (sleep_recorded_days between 0 and 7)
                                                                            -- → 8
```

**둘. 계산 근거를 남길 자리.** 지금은 "수면 84.5점"만 저장되고 **그게 규칙성 때문인지
수면시간 때문인지 사라진다.** AI 해석 문장을 만들 때 다시 계산해야 한다.

아래를 제안한다.

```sql
alter table public.lifestyle_daily_scores
    drop constraint lifestyle_daily_scores_sleep_recorded_days_check,
    add check (sleep_recorded_days between 0 and 8),

    -- 점수의 뼈대. 추이를 그리거나 집계할 값이라 열로 둔다.
    -- 충분성만 필수이고 나머지 셋은 기록이 모자라면 비어 있을 수 있다.
    add column sleep_duration_score  double precision check (sleep_duration_score  between 0 and 100),
    add column sleep_regularity_score double precision check (sleep_regularity_score between 0 and 100),
    add column sleep_stability_score double precision check (sleep_stability_score between 0 and 100),
    add column sleep_jetlag_score    double precision check (sleep_jetlag_score    between 0 and 100),
    -- 가중치의 몇 할이 실제로 채워졌는지. 1.0이 아니면 일부만 반영한 점수다.
    add column sleep_coverage        double precision check (sleep_coverage > 0 and sleep_coverage <= 1),

    -- BMI를 생활 기록에서 가져왔는지 검진에서 가져왔는지.
    -- 검진 값이면 사용자에게 고지해야 하므로 조회 응답까지 내려가야 한다.
    add column bmi_source            text check (bmi_source in ('lifestyle', 'checkup')),

    -- 대사(혈압·공복혈당)는 선택 성분이라 통째로 비어 있을 수 있다.
    add column metabolic_score          double precision check (metabolic_score between 0 and 100),
    add column metabolic_bp_score       double precision check (metabolic_bp_score between 0 and 100),
    add column metabolic_glucose_score  double precision check (metabolic_glucose_score between 0 and 100),
    add column metabolic_coverage       double precision check (metabolic_coverage > 0 and metabolic_coverage <= 1),

    -- 총점에서 실제로 채워진 가중치의 비율. 대사가 없으면 0.9가 된다.
    add column score_coverage        double precision check (score_coverage > 0 and score_coverage <= 1),

    -- 설명에 쓰는 서술 값. 취침·기상 시각, 흔들림(분), 주중·주말 수면 중점 등.
    -- 대사 쪽은 측정일·출처와 혈압 수치가 여기 들어간다.
    -- 프롬프트 작업에 따라 자주 바뀌는 부분이라 열로 고정하지 않는다.
    -- 어느 판으로 만든 값인지는 policy_version이 말해 준다.
    add column sleep_detail          jsonb,
    add column metabolic_detail      jsonb,

    -- 수면 점수가 있으면 충분성과 coverage는 반드시 함께 있다.
    add constraint lifestyle_daily_scores_sleep_parts_check check (
        sleep_score is null
        or (sleep_duration_score is not null and sleep_coverage is not null)
    );
```

**열과 jsonb를 나눈 이유.** 네 하위 점수와 `coverage`는 점수의 뼈대라 자주 바뀌지 않고,
"규칙성이 낮은 사용자 비율" 같은 집계를 SQL로 내려면 열이어야 한다. 반면 취침 시각
문자열이나 `gap_minutes` 같은 서술 값은 프롬프트를 다듬으며 계속 바뀌므로 jsonb가 낫다.
바뀔 때마다 마이그레이션을 하지 않아도 된다.

저장은 이렇게 대응한다.

| 추가 열 | 응답 경로 |
|---|---|
| `sleep_duration_score` | `score.components.sleep.parts.duration.score` |
| `sleep_regularity_score` | `score.components.sleep.parts.regularity.score` |
| `sleep_stability_score` | `score.components.sleep.parts.stability.score` |
| `sleep_jetlag_score` | `score.components.sleep.parts.social_jetlag.score` |
| `sleep_coverage` | `score.components.sleep.coverage` |
| `bmi_source` | `score.components.bmi.source` |
| `metabolic_score` | `score.components.metabolic.score` |
| `metabolic_bp_score` | `score.components.metabolic.parts.blood_pressure.score` |
| `metabolic_glucose_score` | `score.components.metabolic.parts.glucose.score` |
| `metabolic_coverage` | `score.components.metabolic.coverage` |
| `score_coverage` | `score.coverage` |
| `metabolic_detail` | `score.components.metabolic.parts` 에서 위 값을 뺀 나머지 |
| `sleep_detail` | `score.components.sleep` 에서 위 값을 뺀 나머지 |

`sleep_detail`에는 취침·기상 시각이 들어간다. 개인 건강정보이므로 **지금처럼 서버 전용으로
두고 앱 응답에 그대로 싣지 않는다.** 현재 RLS와 권한 설정을 바꿀 필요는 없다.

다만 `bmi_source`와 `bmi_date`는 예외다. **검진 BMI로 계산한 경우 사용자에게 고지해야 하므로**
`GET /api/health/score` 응답에 함께 내려가야 한다.

고지 문구는 서비스가 만들어 `components.bmi.notice`에 넣어 준다. 앱은 그대로 쓰면 되고
비어 있으면 고지할 것이 없다는 뜻이다. 저장은 `bmi_source`·`bmi_date`만 하고 문구는
조회 시점에 다시 만들어도 된다 — 화면에서 조립하지만 않으면 된다. 기준 문서의
[검진 BMI로 계산했으면 사용자에게 밝힌다](오늘의_건강_종합점수_기준.md#검진-bmi로-계산했으면-사용자에게-밝힌다)를 볼 것.

### `policy_version`이 바뀐다

`heapy-lifestyle-v1` → `heapy-health-v1`. 기존 v1 행을 어떻게 할지 정해야 한다.
점수 산출 방식이 달라 **같은 그래프에 이어 그리면 사용자에게 원인 모를 계단이 생긴다.**

## 5. 결정이 필요한 것

**활동의 `max`** — 걸음과 운동 중 나은 쪽을 쓴다(v1 그대로). 8,000걸음을 채우면 운동을
전혀 하지 않아도 활동 100점이다. 의도인지 확인이 필요하다.

**재정규화 상한** — 수면 하위 성분이 빠지면 남은 가중치를 다시 정규화한다. 시각 기록이
모자란 신규 사용자는 규칙성 감점을 받지 않아 **기록이 적을수록 유리해질 수 있다.**

## 6. 분석 문장이 자정에 사라진다

점수와 분석 문장의 저장 방식이 다르다. **점수는 영구, 문장은 하루짜리다.**

| | 저장 위치 | 영속성 |
|---|---|---|
| 점수 | `public.lifestyle_daily_scores` | 영구 (최근 7일 유지) |
| 분석 문장 | Redis `HealthAnalysisCache` | **다음 한국 자정 만료** |

`private.health_analysis_runs`에는 상태(`pending`·`generating`·`generated`·`data_insufficient`·
`failed`)만 남고 **문장 자체를 담는 열이 없다.** 결과는 Redis에만 있고 조회도 오늘 것만
돌려준다.

```java
public JsonNode get(UUID user, LocalDate day, String category) {
    if (!day.equals(LocalDate.now(ZONE))) return null;   // 오늘이 아니면 아예 안 준다
```

그래서 이런 일이 생긴다.

- **어제 브리핑을 볼 수 없다.** 지난 흐름을 보여주는 화면을 만들 수 없다
- **Redis가 비면 문장이 사라진다.** `health_analysis_runs`에는 `generated`로 남아 있는데
  내용은 없는 상태가 된다. 재시작·장애·TTL 만료 때마다 발생한다

### `health_analysis_runs`에 결과 열을 더한다

새 테이블(`daily_health_briefings`)을 만드는 대신 **기존 표에 열 하나를 더하는 쪽**으로 간다.
상태 관리·중복 방지·무효화(`health_analysis_invalidations`)가 이미 여기 붙어 있어, 새 표를
만들면 그 로직을 다시 짜야 한다.

```sql
alter table private.health_analysis_runs
    -- LLM이 만든 문장. Redis는 앞단 캐시로만 쓰고 원본은 여기 남긴다.
    -- 크기 한도는 캐시와 같게 본다(65,536바이트).
    add column result jsonb,

    -- 카테고리를 넓힌다. 지금 제약에 6개가 박혀 있어 새 값을 저장하는 순간 실패한다.
    drop constraint health_analysis_runs_category_check,
    add constraint health_analysis_runs_category_check check (
        category in ('bio','activity','nutrition','sleep','checkup','overall','briefing')
    );
```

조회는 Redis를 먼저 보고, 없으면 이 열에서 읽어 캐시를 다시 채우면 된다. 과거 날짜는
캐시를 건너뛰고 바로 읽는다.

### `score`는 이 제약과 무관하다

점수는 `LifestyleScoreScheduler` → `LifestyleScoreStore.insert()`로 `lifestyle_daily_scores`에
직접 쓴다. `HealthAnalysisRunner`를 타지 않으므로 `category` CHECK에 `'score'`를 넣을 필요가
없다.

**다만 점수 계산을 FastAPI로 옮기면서 `HealthAnalysisRunner`를 재사용하기로 한다면 이야기가
달라진다.** 그때는 `'score'`도 제약에 함께 넣어야 하고, 넣지 않으면 저장 시점에 제약 위반으로
실패한다. 어느 경로로 갈지 먼저 정할 것.

## 7. 심박수 상시 측정을 켜기 전에

심박수는 아직 점수에도 해석에도 쓰지 않는다. 쓰려면 삼성헬스의 **'심박수 항상 측정'**이
필요한데, **켜기 전에 집계 설계를 먼저 정해야 한다.** 그냥 켜면 분석이 죽는다.

### 지금 데이터로는 아무것도 못 한다

실제 1년치 내보내기(365일)를 확인한 결과다.

| 항목 | 실측 |
|---|---|
| `heart_rate` 레코드 | **22건 / 8일** — 나머지 357일은 없음 |
| 측정 형태 | 같은 분에 2~7건씩 몰림, `seriesData` 비어 있음, min/max 0 |
| 값의 범위 | 78~114 bpm — 안정시라기에는 높다 |
| 출처 | `com.sec.android.app.shealth` 단일 기기 |

**자동이 아니라 사용자가 앱에서 직접 잰 기록이다.** 안정시 심박수도, 기준선도 만들 수 없다.

한편 **운동 기록 안에는 심박수가 있다.** `exercise.json`의 `sessions[].log[]`에 10초 간격으로
들어 있고 183세션 중 72세션, 표본 6,313개다. `meanHeartRate`·`maxHeartRate`도 세션 단위로
있다. 다만 **로그가 운동 종료 시각에 정확히 끊긴다(0건 예외 없음).** 그래서 운동 후 회복
심박수(HRR)는 지금 데이터로 잴 수 없다.

### 켜면 1만 행 상한에 걸린다

삼성 공식 문서 기준 '항상 측정'은 **매 초** 측정한다(SDK가 초 단위로 돌려주는지는 재확인
필요 — 아래 참조).

```
1초 간격 = 하루 86,400건 = 1년 3,150만 건

HealthAnalysisSnapshot: HealthPeriod.of("1y", ...) 로 전 지표 1년치를 읽고
                        total > 10000 이면 "분석 입력 한도 초과" 예외
→ 심박수 약 2시간 47분 치면 상한을 넘긴다
```

**점수와 AI 해석이 전부 실패한다.** `HealthSyncInput`도 `heart_rate_bpm`을 행 단위로 저장하므로
`lifestyle_bio`가 사용자 한 명당 연 3천만 행으로 불어난다.

### 먼저 확인할 것

상시 측정을 켜고 2~3일 뒤 다시 내보내 아래를 본다. 이게 나와야 설계를 정할 수 있다.

- `heart_rate.json`의 레코드 수와 **`seriesData`의 내용** — 지금은 비어 있다. 여기에 시계열이
  담겨 나오면 레코드 수는 적고 구간 데이터가 들어오는 형태라 양의 그림이 달라진다
- 실제 표본 간격 — 초 단위인지, 삼성이 집계해 주는지
- **운동 종료 이후 구간이 덮이는지** — HRR 가능 여부가 여기서 확정된다
- 계단 이벤트(`floors_climbed`, 중앙값 27초, 340건/74일)와 시각이 겹치는지

### 집계 지점을 정해야 한다

원시 샘플은 `/internal`로 넘길 수 없다. 어디선가 줄여야 한다.

| | 앱에서 줄인다 | 서버가 원시를 받아 줄인다 |
|---|---|---|
| 서버 부담 | 없음 | 3천만 행 저장 |
| 프라이버시 | 원시가 나가지 않음 | 원시를 보관 |
| 규칙 변경 | 앱 배포 필요 | 언제든, 소급 적용 가능 |

HRR처럼 기준이 확립된 지표는 앱에서, 우리가 계속 다듬을 지표는 서버에서 — 이렇게 섞는 것도
방법이다. **위 확인 결과가 나온 뒤에 정한다.**

## 8. 알아둘 것

**수면은 창보다 하루 짧게 잡힌다.** `normalize_window`가 분석일 당일 기록을 빼고,
자정 이후에 끝난 수면도 `cutoff`로 걸러낸다. 전날 밤에 자 분석일 아침에 깬 기록이 여기
해당한다. 그래서 충분성의 창을 **8일**로 잡아 최근 한 주가 온전히 남게 했다.
`sleep_recorded_days`의 상한을 8로 넓혀야 하는 이유다.

**폐기 대상.** `LifestyleScoreCalculator.java`와 그 테스트. FastAPI가 같은 값을 내므로
두 곳에 두면 갈라진다. `LifestyleScoreService`·`Scheduler`·`Store`는 호출부만 바꾸면 남는다.

**배포 순서.** FastAPI를 먼저 올려야 한다. Spring이 `category: "score"`를 먼저 보내면
422를 받는다. FastAPI 배포는 저장소 변수 `DEPLOY_ENABLED`가 `true`여야 동작한다.

**계약 테스트.** `tests/internal/test_health_analysis.py`에 점수 응답 형식 테스트가 있다.
FastAPI CI가 매번 돌리므로 응답 형식이 조용히 바뀌지 않는다.
