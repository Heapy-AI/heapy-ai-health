# 다중 컬렉션 병렬 검색 및 결과 병합 방법론

- 작성자: 김진우
- 상태: 초기 구현 완료, 검색 상수 및 운영 임계값은 데이터 적재 완료 후 결정

## 1. 목적

HEAPY의 벡터 검색에서 별도의 Sub-intent 또는 Collection Router 분류기를 두지 않고, 검색 대상 Pinecone namespace를 병렬로 조회한 뒤 결과를 하나의 근거 목록으로 병합한다.

이 방법은 다음 문제를 줄이기 위해 사용한다.

- Sub-intent 학습 데이터 구축 및 모델 운영 비용
- 잘못된 컬렉션으로 라우팅하여 필요한 근거를 검색하지 못하는 문제
- 건강검진, 질병, 복약 등 여러 주제가 섞인 복합 질문 처리의 어려움

## 2. 적용 범위

최상위 Intent 분류기는 유지한다.

| Intent | 검색 처리 |
|---|---|
| `simple_lookup` | 다중 namespace 검색 후 일반 정보 근거 구성 |
| `comprehensive` | 다중 namespace 검색과 사용자 개인 데이터 조회 결과를 결합 |
| `general_chat` | 벡터 검색을 수행하지 않음 |
| `ignore` | 건강 서비스와 완전히 무관한 질문이므로 벡터 검색 없이 고정 응답 |

제거하거나 생략하는 대상은 최상위 Intent 분류기가 아니라, 검색할 컬렉션을 고르는 Sub-intent 분류 단계다.

## 3. 전체 처리 흐름

```text
사용자 질문
  → 최상위 Intent 분류 및 독립 Safety 정책 생성
  → 질문 임베딩 1회 생성
  → 검색 가능한 namespace 병렬 조회
  → 컬렉션별 검색 후보 수집
  → 결과 병합
  → 중복 제거
  → 최소 관련도 조건 적용
  → 전체 후보 정렬
  → 컬렉션별 최대 선택 개수 적용
  → 최종 근거 청크 선택
  → 검색 결과 존재·최소 기준·명시 대상 일치 검사
  → 근거가 있는 질문 항목만 최종 답변 생성
  → 근거 충족도·안전 정책 준수 여부 사후 감사
```

## 4. 검색 대상 관리

검색 대상은 로컬 청크 폴더를 자동 탐색하는 방식보다 환경설정에 명시하는 방식을 우선한다. 팀원의 로컬 환경에 원천 청크가 없어도 동일한 Pinecone namespace를 조회할 수 있어야 하기 때문이다.

예시:

```text
SEARCH_COLLECTIONS=health_checkup_info,disease_info,medication_info,drug_interaction_info
```

검색 시점에 데이터가 없거나 아직 생성되지 않은 namespace는 빈 검색 결과로 처리한다. 하나의 빈 namespace 때문에 전체 검색을 실패시키지 않는다.

개인 식별정보, 개인 검진 기록 및 개인 복약 기록은 공용 Pinecone namespace에 저장하지 않는다. 해당 정보는 인증된 사용자 데이터 저장소에서 조회해 `comprehensive` 경로에서만 결합한다.

## 5. 질문 임베딩 재사용

질문 임베딩은 요청당 한 번만 생성한다. 생성된 동일 벡터를 모든 namespace 검색에서 재사용한다.

```text
잘못된 방식
namespace A 검색 전 임베딩
namespace B 검색 전 임베딩
namespace C 검색 전 임베딩

적용 방식
질문 임베딩 1회
  ├─ namespace A 검색
  ├─ namespace B 검색
  ├─ namespace C 검색
  └─ namespace D 검색
```

모든 namespace는 동일한 Pinecone 인덱스, 임베딩 모델, 벡터 차원 및 거리 척도를 사용해야 한다.

## 6. 병렬 검색

각 namespace 검색은 서로 독립적인 네트워크 요청이므로 병렬로 실행한다. 검색 전에 임베딩을 완료하고, 각 작업에는 동일한 질문 벡터와 컬렉션별 후보 개수를 전달한다.

각 검색 결과에는 다음 메타데이터를 보존한다.

| 필드 | 설명 |
|---|---|
| `collection` | 결과가 검색된 namespace |
| `record_id` | namespace 내부의 Pinecone 레코드 ID |
| `score` | Pinecone 유사도 점수 |
| `source` | 원천 URL 또는 문서 식별자 |
| `source_label` | 사용자에게 표시할 출처명 |
| `chunk_text` | 검색된 청크 본문 |

일부 namespace가 빈 결과를 반환하면 나머지 결과로 계속 처리한다. 네트워크 오류와 빈 결과는 구분해 기록한다.

## 7. 결과 병합

컬렉션별 검색 결과를 하나의 후보 목록으로 연결한다.

```text
health_checkup_info 후보 ┐
disease_info 후보        ├─ 전체 후보 목록
medication_info 후보     │
drug_interaction 후보    ┘
```

후보 병합 후 다음 순서로 처리한다.

### 7.1 중복 제거

우선순위에 따라 동일 청크를 판별한다.

1. 안정적인 원천 문서 ID와 청크 ID 조합
2. 원천 ID와 원문 위치 조합
3. 공백을 정규화한 청크 본문의 해시

Pinecone 레코드 ID는 namespace 안에서만 고유할 수 있으므로, 단순 `record_id`만으로 서로 다른 namespace의 중복을 판정하지 않는다.

### 7.2 최소 관련도 적용

관련도가 지나치게 낮은 후보를 제거한다. 임계값은 전체 데이터가 적재된 후 실제 질의 평가를 통해 결정한다. 데이터 준비 전에는 값 자체를 확정하지 않고 설정 항목과 처리 위치만 마련한다.

### 7.3 전체 후보 정렬

현재 구조처럼 모든 namespace가 동일한 인덱스와 임베딩 설정을 사용한다면 Pinecone 유사도 점수를 기준으로 전체 후보를 우선 정렬할 수 있다.

서로 다른 임베딩 모델이나 거리 척도를 사용하는 인덱스를 함께 검색할 경우 원점수를 직접 비교하지 않는다. 이 경우 공통 리랭커로 재채점해야 한다.

### 7.4 컬렉션 편중 제한

하나의 컬렉션이 최종 근거를 모두 차지하지 않도록 컬렉션별 최대 선택 개수를 둘 수 있다.

컬렉션별 최소 선택 개수는 강제하지 않는다. 질문과 무관한 컬렉션의 청크가 근거에 포함될 수 있기 때문이다.

### 7.5 최종 근거 선택

정렬과 편중 제한을 통과한 후보 중 최종 개수만 LLM에 전달한다. 컬렉션별 후보 개수, 최소 관련도, 컬렉션별 최대 개수 및 최종 개수는 데이터 적재 완료 후 조정한다.

## 8. RRF와 리랭킹 적용 기준

RRF는 동일하거나 유사한 문서가 여러 검색기에서 검색될 때 순위를 결합하는 데 유용하다. 서로 다른 주제의 namespace가 각각 고유 문서를 반환하는 현재 구조에서는 RRF만 적용하면 각 컬렉션의 같은 순위 문서가 비슷하게 취급될 수 있다.

초기 구현은 다음 방식을 사용한다.

```text
동일 임베딩·동일 거리 척도
  → Pinecone 유사도 기준 전체 정렬
```

검색 품질이 충분하지 않으면 다음 단계로 공통 리랭커를 추가한다.

```text
병렬 검색 후보
  → 질문과 각 청크를 공통 기준으로 재채점
  → 전체 재정렬
  → 최종 근거 선택
```

리랭커 도입 여부는 검색 Recall과 정답 근거 순위가 부족한 것이 확인된 후 결정한다.

## 9. LLM 문맥 구성

최종 청크에는 컬렉션, 점수 및 출처를 함께 표시한다.

```text
[컬렉션: health_checkup_info]
[유사도: 검색 점수]
[출처: 건강검진 검사항목별 판정기준]
공복혈당은 일정 시간 금식한 뒤...

[컬렉션: medication_info]
[유사도: 검색 점수]
[출처: 의약품 복약정보]
일부 의약품은 혈당에 영향을 줄 수 있으며...
```

답변에 사용한 출처는 최종 선택된 청크에서만 생성한다. 검색 후보에는 있었지만 최종 선택되지 않은 청크의 출처를 응답에 포함하지 않는다.

## 10. 오류 및 빈 결과 처리

다음 상태를 구분한다.

| 상태 | 처리 |
|---|---|
| 일부 namespace 결과 없음 | 나머지 결과로 계속 진행 |
| 모든 namespace 결과 없음 | 근거 없음 응답 |
| 일부 namespace 검색 오류 | 오류 namespace를 기록하고 운영 정책에 따라 부분 결과 또는 전체 오류 처리 |
| 질문 임베딩 실패 | 전체 검색 실패 처리 |
| Pinecone 연결 실패 | 전체 검색 실패 처리 |

의료정보 서비스이므로 일부 검색 오류를 숨긴 채 완전한 검색 결과처럼 응답하지 않는다. 부분 결과 사용 여부를 응답 메타데이터와 로그에서 확인할 수 있어야 한다.

## 11. 데이터 준비 전 검증

전체 namespace가 적재되지 않아도 가짜 검색 결과를 사용해 다음 항목을 단위 테스트할 수 있다.

- 질문 임베딩이 요청당 한 번만 실행되는지
- 설정된 namespace가 각각 한 번씩 호출되는지
- 빈 검색 결과를 정상 처리하는지
- 중복 청크가 제거되는지
- 전체 후보가 점수 기준으로 정렬되는지
- 컬렉션별 최대 개수가 적용되는지
- 최종 반환 개수가 제한되는지
- 일부 검색 실패와 전체 검색 실패를 구분하는지
- 최종 근거에 컬렉션과 출처가 포함되는지

실제 Pinecone 통합 테스트는 현재 적재된 namespace만으로 먼저 수행할 수 있다. 나머지 namespace가 적재되면 동일한 코드에 검색 대상만 활성화한다.

## 12. 데이터 적재 완료 후 조정 항목

다음 값은 현재 확정하지 않는다.

- 컬렉션별 1차 후보 개수
- 최소 유사도
- 컬렉션별 최대 선택 개수
- LLM에 전달할 최종 청크 개수
- 리랭커 사용 여부와 후보 개수
- 일부 namespace 장애 시 부분 결과 허용 여부

실제 질문 평가셋으로 다음 지표를 측정해 결정한다.

| 지표 | 확인 목적 |
|---|---|
| Recall@k | 정답 근거가 후보 안에 포함되는지 |
| MRR 또는 정답 근거 순위 | 정답 근거가 얼마나 위에 배치되는지 |
| 컬렉션별 선택 비율 | 특정 컬렉션 편중 여부 |
| 근거 충실성 | 답변이 선택한 청크에 근거하는지 |
| 답변 정확도 | 최종 사용자 질문에 적절히 답하는지 |
| p50·p95 검색 지연시간 | 병렬 검색의 실제 응답속도 |
| 요청당 검색량 | Pinecone 사용량과 비용 변화 |

## 13. 구현 현황

초기 구현에서 다음 파일을 수정하거나 추가했다.

| 파일 | 변경 내용 |
|---|---|
| `app/core/config.py` | 검색 namespace와 조정 가능한 검색 설정 추가 |
| `app/services/vector_search.py` | 임베딩 재사용, 병렬 검색 및 후보 수집 구현 |
| `app/services/search_result_merger.py` | 중복 제거, 정렬, 컬렉션 편중 제한 구현 |
| `app/services/grounded_rag.py` | 청크 ID 인용 답변 생성 및 조건부 별도 근거 검증 구현 |
| `app/services/rag.py` | 컬렉션·점수·출처가 포함된 문맥 구성 |
| `app/schemas/health_chatbot.py` | 통합 검색 요청·응답 스키마 추가 |
| `app/routers/ask.py` | 통합 검색 및 통합 RAG 엔드포인트 연결 |
| `tests/test_multi_collection_search.py` | 가짜 검색 결과 기반 단위 테스트 추가 |
| `tests/test_grounded_rag.py` | 인용 누락·허위 인용·근거 없는 주장 차단 테스트 추가 |
| `docs/api_spec.md` | 통합 검색 API 계약 기록 |
| `docs/pipeline.mmd` | Sub-intent 대신 병렬 검색 흐름 반영 |
| `docs/pipeline_state_design.md` | 다중 검색 상태와 오류 정책 반영 |
| `docs/node_io_spec.md` | 검색 노드 입출력 변경 반영 |

기존 단일 컬렉션 `/search`, `/ask`는 적재 및 검색 품질 점검을 위해 유지한다. 다중 컬렉션 검색은 `/search/combined`, `/ask/combined`로 추가했으며, 전체 데이터 검증 완료 후 챗봇 기본 경로에 연결한다.

## 14. 최종 결정 사항

- 최상위 Intent 클래스 4개는 유지하고 라벨 경계를 조정한 Intent v7을 사용한다.
- 별도 Sub-intent 또는 Collection Router 모델은 우선 만들지 않는다.
- 검색 대상 namespace를 병렬 조회한다.
- 질문 임베딩은 요청당 한 번만 생성하고 재사용한다.
- 검색 결과는 중복 제거, 관련도 정렬 및 컬렉션 편중 제한 후 LLM에 전달한다.
- 최종 답변 전 별도 LLM 근거 계획은 사용하지 않는다. 검색 결과 존재·최소 유사도·명시 대상 일치를 코드로 검사하고, 복합 질문은 근거가 있는 항목부터 답한다. `emergency` 역시 검색을 중단하지 않고 긴급 행동 안내 뒤에 확인 가능한 요청 정보를 제공한다. 답변 후 근거 충족도와 안전 정책 준수 여부는 본문을 교체하지 않는 사후 감사로 기록한다.
- 검색 상수와 리랭커 도입 여부는 전체 데이터 적재 및 평가셋 준비 후 확정한다.
